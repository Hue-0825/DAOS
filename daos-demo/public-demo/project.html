01 / 전체 구조

주문은 이렇게 배송으로 이어집니다

  1. 스토어

    주문을 접수합니다. 같은 요청을 다시 보내면 처음 받은 접수 번호를 돌려줍니다.

  2. 메인 관제센터

    주문을 지역별로 모아 허브에 보냅니다. 시연 시간과 기사 서버 연결을 제어합니다.

  3. 지역 허브

    시·도와 시간대별로 배차합니다. 기사 기기에 최신 작업표가 저장됐는지 확인합니다.

  4. 기사 앱

    당일과 다음 날 작업표를 받아 둡니다. 배송 결과는 서버가 접수를 확인할 때까지 기기에 보관합니다.

별도 로봇 관제실

로봇 20대가 상자 54개를 하차하고, 운반·분류를 거쳐 트럭에 싣습니다.

  • 정상 운전 선행 공정이 끝났는지, 이동할 칸이 비어 있는지 확인합니다.
  • 연결 끊김 경고가 표시되는 동안에도 자동 저장된 작업표로 운행을 이어갑니다. 시연에서 작업표의 유효시간은 마지막 갱신부터 45초입니다.
  • 연결 복구 장애 직전의 중앙 기록, 현장 인계 기록, 가상 스캔을 대조합니다. 기록이 다르면 해당 상자를 보류합니다.

공식 규격 릴리스

실물 장비에서 확인할 항목

  • 통로 사용 권한 두 로봇의 권한이 겹치지 않는지, 시계 오차나 연결 끊김이 있어도 만료를 확인하는지 검증합니다.
  • 장비 안전 장애물 감지, 긴급 정지, 구역 제어, 실제 스캐너 측정을 시험합니다.
  • 실험 도구 ROS 2와 Gazebo로 장비 동작을, MAPF 창고 지도로 통로 배치를 비교할 수 있습니다.

Gazebo와 ROS 조합 · Moving AI 창고 지도 · 하이브리드 논리 시계

산업 사례에서 확인한 내용

  • Ocado Erith 공식 발표에 따르면 로봇 세 대가 충돌해 화재가 발생했습니다. 발표문에는 중앙 서버의 장애 여부가 명시돼 있지 않습니다.
  • Amazon·LG CNS 공개 자료는 로봇 이동 최적화와 여러 종류의 로봇 통합 운영을 설명합니다. 장애 대응 성능을 비교하려면 별도 자료가 필요합니다.

Ocado 공식 발표 · Amazon Science · LG CNS RX · Open-RMF

03 / 검증 계획

같은 주문과 장애로 비교합니다

  1. 기준선

    주문, 로봇 배치, 장애 시점을 맞춰 DAOS OFF와 ON을 비교합니다.

  2. 기사 앱

    배송을 기록한 뒤 다시 연결합니다. 재전송, 작업 순서 위반, 이전 배차 버전을 시험합니다.

  3. 로봇 관제실

    연결을 끊는 순간에도 DAOS로 운행이 이어지는지 확인합니다. 백업이 만료됐거나 스캔 기록이 다를 때는 정지와 보류를 확인합니다.

  4. 계측

    장애 중 처리량과 정상화 시간을 비교합니다. 중복·누락, 보류, 통로 충돌 건수도 기록합니다.

비용과 처리량 예시

시간당 2,000라인을 처리하는 센터에서 30분 동안 장애가 났다고 가정한 계산입니다. 장애 후 정상화 시간은 기존 40분, DAOS 적용 시 5분으로 두었습니다.

장애 1회당 예상 처리 손실
1,800 → 450라인
예상 손실 감소율
75%
연 6회 장애 시 직접 절감 추정
약 776.5만 원

절감액에는 긴급 대응비와 인건비를 반영했습니다. 손익분기점을 계산하려면 구축비와 연간 운영비를 추가해야 합니다.

장애가 2시간 이어지면 초반 처리율 60%를 30분 유지할 때 예상 손실은 2,550라인입니다. 5분만 유지하면 약 2,800라인으로 늘어납니다. 이후 처리율은 두 경우 모두 30%로 가정했습니다.
