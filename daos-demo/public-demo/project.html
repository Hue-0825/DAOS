01 / 정상 · 장애 · 복구

상자 한 개를 따라가 봅니다

  1. 01 / 미리 받기옮길 상자와 사용할 통로를 받습니다

    중앙이 상자 A-01-01의 이동 작업을 내려보냅니다. 통로 사용 권한에는 만료 시간이 붙습니다.

  2. 02 / 이어가기조건이 맞으면 운반을 계속합니다

    하차가 끝났고, 받은 권한이 유효하고, 다음 칸이 비어 있으면 상자를 옮깁니다. 조건이 모자라면 기다립니다.

  3. 03 / 확인하기상자가 도착했는지 대조합니다

    전환을 시작하며 설비가 멈춘 순간의 상자 위치를 메인 서버로 먼저 보냅니다. 중앙은 받은 위치를 장애 직전 기록과 현장 작업 이력에 맞춰 봅니다. 일치하면 처리한 지점부터 이어갑니다.

기사 앱도 같은 원리입니다. 지역 허브가 배차한 배송 정보를 기기에 저장합니다. 연결이 끊기면 저장된 작업표로 배송하고, 재연결 후 서버가 받은 기록만 전송 대기 목록에서 뺍니다. 창고 시연은 별도의 가상 작업표를 사용하며 메인 관제센터의 서버 연결 상태를 읽습니다. 로봇 화면의 장애 버튼은 창고 시연에 적용됩니다.

02 / 스마트 물류 보고서 2.2 · 그림 1 재구성

중앙은 계획하고, 현장은 움직입니다

평상시에는 작업과 권한이 중앙에서 현장으로 내려갑니다. 연결이 돌아오면 현장의 기록이 중앙으로 올라갑니다.

01 중앙
주문을 작업으로 바꾸고 로봇에 통로 사용 권한을 미리 발급합니다.
02 구역 엣지
창고 안의 장치가 이동 칸을 조정하고 로봇의 기록을 복제합니다.
03 로봇
앞 공정과 권한을 확인해 움직이고 완료 기록을 남깁니다.
보고서 설계와 브라우저 시연의 차이

보고서는 정상 시 향후 5분 범위의 권한 위임, 하트비트 3회 누락 감지, 작업·자원 관계를 이용한 판단(DRG), 같은 구역의 로봇 간 협상을 제안합니다. 웹은 전환 시작 시 1초 정지하며, 복구 시 상자 위치 전송과 기록 대조를 마친 뒤 운전을 재개합니다. 서버가 끊기면 이미 내려받은 작업표로 상차까지 이어갑니다. 공정 순서와 구역 권한, 이동 칸 예약은 계속 확인합니다. VDA 5050의 Base는 관제가 명시적으로 승인한 경로이며 이 시연의 구역·격자 권한과 범위가 다릅니다.

실제 장비에서는 구역 소형 PC의 MQTT 중계와 시각 동기화, 로봇 카메라·작업자 PDA의 물품 확인, 로봇 간 직접 협상을 검증할 계획입니다. 웹의 3중 대조는 중앙 기록·로봇 및 엣지 로그·가상 위치 증거를 비교하며, 대조 후 새 운전 세대(에폭)를 발급합니다.

보고서 3.2 · 4.1–4.3

무엇을 저장하고, 언제 움직이나요?

중앙이 정상일 때 권한을 저장하고, 장애 중에는 허용된 작업만 이어갑니다. 연결이 돌아오면 기록을 대조해 새 에폭에서 운전을 재개합니다.

① 미리 받은 점유권
로봇, 자원, 작업 목록, 유효 시작·종료 시각과 에폭을 묶습니다. 아래 예시에서 AMR-17은 에폭 12에 B3 통로를 10:15부터 10:17까지 두 작업에 사용할 권한을 받습니다.
② 작업 판별 · DRG
초록은 선행 작업이 완료됐고 예상 실행 시간과 여유시간을 덮는 권한이 있는 경우입니다. 노랑은 같은 구역에서 엣지의 추가 승인이 필요한 경우입니다. 승인 전에는 대기합니다. 선행 작업 미완료, 만료, 협상 불가이면 빨강으로 보류합니다.
③ 3중 대조와 에폭 펜싱
장애 직전 중앙 기록, 로봇의 추가 전용 로그와 엣지 복제본, 마지막 실물 스캔을 비교합니다. 일치한 작업만 확정하고 증거가 부족하면 보류합니다. 새 에폭이 발급되면 이전 에폭의 권한과 지연된 기록을 거부합니다.
점유권과 작업 로그 JSON 예시

점유권 · 시각은 날짜와 시간대까지 기록합니다.

{
  "leaseId": "L-20261110-0042",
  "robotId": "AMR-17",
  "epoch": 12,
  "resource": "AISLE-B3",
  "from": "2026-11-10T10:15:00+09:00",
  "until": "2026-11-10T10:17:00+09:00",
  "taskIds": ["T-88121", "T-88122"]
}

작업 로그 · AMR-17이 ST-04에서 하역 후 R-2210 랙을 스캔한 예입니다.

{
  "eventId": "12/AMR-17/5531",
  "taskId": "T-88121",
  "epoch": 12,
  "seq": 5531,
  "event": "DROP_DONE",
  "hlc": "2026-11-10T10:16:42.118+09:00#3",
  "node": "ST-04",
  "rackId": "R-2210",
  "scan": "OK"
}

taskId는 작업 전체를, eventId는 개별 기록을 식별합니다. 같은 작업에도 여러 이벤트가 생깁니다. 재전송은 같은 키로 한 번만 처리하고, 같은 키에 다른 내용이 도착하면 확인을 보류합니다. HLC는 인과 순서 추적에 쓰고 점유권 만료는 시간 오차를 감안한 별도 검사로 판단합니다. HLC 원 논문 ↗

브라우저에서 검증할 수 있는 범위

시연은 공정 순서와 구역 사용 권한, 현재 점유 칸으로 DRG를 단순화했습니다. 중앙은 연결 중 작업표를 10초마다 갱신합니다. 장애 중에는 마지막 작업표에 포함된 작업과 해당 운전 세대의 구역 권한을 확인합니다. 공유 통로 예약은 엣지가 담당하고, 같은 칸에 둘이 진입할 수 없도록 시뮬레이터가 점유를 관리합니다.

중앙을 끊은 뒤 공유 통로 엣지를 끊으면 해당 통로가 필요한 작업이 보류됩니다. 현장 로그와 가상 스캔을 대조해 새 에폭으로 전환하는 과정까지 브라우저에서 확인할 수 있습니다.

04 / 실험과 비용 · 보고서 5.4, 6장

장애가 같을 때 무엇이 달라지는가

로봇 수와 작업표, 장애 시점과 지속시간을 맞춰 DAOS를 끈 경우와 켠 경우를 비교합니다.

장애 1회 직접 손실 감소 추정
약 129.4만 원

긴급 대응비 121.5만 원 + 수동 복구 인건비 약 7.9만 원

초기 장비와 월 운영비 예시
약 40만 원 / 월 약 2.3만 원

엣지 2대 기준. 월 운영비는 중앙 VM 상한과 전력비를 합산한 값입니다.

비용 계산과 보고서 그림 3의 차이

장애 30분 동안 처리율은 기존 0%, DAOS 60%로 가정했습니다. 복구 구간은 기존 40분·처리율 40%, DAOS 5분·처리율 70%를 사용했습니다. 긴급 대응비는 1,350줄 × 30% × 3,000원입니다. 수동 복구 인건비는 시간당 25,000원으로 기존 5명 × 40분과 DAOS 적용 시 1명 × 10분을 비교했습니다.

그림 3의 DAOS 복구 처리율 30%를 적용하면 미처리 약 517줄, 직접 손실 감소 약 123.4만 원입니다. 월 운영비 예시는 VM 월 2만 원과 엣지 두 대 각 10W, 24시간 가동, 200원/kWh를 가정했습니다. 같은 장애를 연 6회 가정하면 운영비 차감 전 직접 절감 추정액은 약 776.5만 원입니다. 개발·연동·유지보수는 별도이며 실제 장애 이력과 견적을 확보한 뒤 투자 회수 기간을 산정합니다.

실물 검증에서 측정할 항목

장애 중 처리량 유지율, 정상화 시간, 중복·누락, 확인 보류, 통로 충돌·교착을 기록합니다. 보고서의 장애 중 처리량 60% 이상, 정상화 5분 이내, 중복 0건은 검증 목표입니다. 실제 장비에서는 안전 정지, 센서와 스캐너, 엣지 장애 및 시계 오차를 별도로 시험합니다.

보고서의 실증 계획은 격자 시뮬레이션 → 구역 장치 MQTT 연결 → 소형 로봇 3대 시험 순입니다. 시연은 가상 주문과 작업 이력을 쓰며, 협력 물류센터의 실제 데이터는 비식별 집계값으로 기준선을 보정하는 데 사용할 계획입니다.

물류 현장 적용

앞 공정의 결과를 다음 로봇이 확인합니다

Bayou의 의존성 검사를 선행 조건 확인에 참고한 DAOS 응용 설계입니다. 실제 센서나 로봇의 검출 성능을 입증한 것은 아닙니다. 현장 통신·스캔·설비는 브라우저에서 모사합니다.
