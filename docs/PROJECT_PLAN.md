# DAOS 프로젝트 요구사항 및 개발 로드맵 v1.0

## 1. 팀 합의 사항
- 목표: 특정 제조사에 종속되지 않는 **중앙 서버 장애 대응 범용 백업·자율운영 시스템**.
- 핵심 아이디어: 장애 시 **로봇별 작업 의존성**과 **공유 자원 점유권**을 분석하여 충돌 위험이 낮고 승인된 작업만 분산 실행한다.
- 복구 시 **물품의 실제 위치와 작업 이력**을 비교해 중복 작업을 방지한다.
- 배송기사 앱은 **향후 2~3일치 확정 작업 데이터**를 미리 저장해 오프라인 운영을 지원한다.
- 로봇과 물류센터 운영은 웹 시뮬레이터/관제 화면으로 구현한다.

## 2. 장애 범위와 안전 조건
| 상황 | 목표 동작 | 제한 |
|---|---|---|
| 중앙 서버 장애, 로컬 네트워크 정상 | 백업 모드 자동 전환 | 확정되고 유효한 작업만 수행 |
| 기사 단말기 오프라인 | 저장된 배송 조회 및 이벤트 로컬 기록 | 주소 변경/미확정 작업 보류 |
| 로봇 FMS 장애 | 소형 비상 관제에서 작업 의존성·자원 점유 판단 | 공유 통로 점유 불명·안전 검증 불가 시 정지 |
| 중앙 서버 복구 | 이벤트 재생·멱등성 검증·물품 위치 대조 | 불일치는 수동 확인 대기 |
| 보안 침해 의심 | 자동 동기화 차단, 격리 상태 알림 | 오염된 데이터 무분별한 복제 금지 |

## 3. 공통 데이터 모델 (초안)
- Order: id, destination, status, confirmedAt, updatedAt
- Task: id, orderId, type, assignedTo, dependencies[], resourceIds[], status, version, approvedUntil
- Resource: id, type, occupiedBy, leaseUntil, version
- InventoryItem: id, sku, recordedLocation, observedLocation, lastScanAt
- WorkEvent: eventId, taskId, actorId, eventType, occurredAt, source, sequence
- ServerState: component, health, detectedAt, mode

모든 메시지에 고유 식별자를 부여하고, 장애 중 처리한 이벤트는 **추가 전용 로그**로 기록한다.

## 4. 최초 시연 시나리오
1. 중앙 서버 정상 작동, 확정 작업을 로컬로 사전 복제
2. 중앙 서버 강제 중단 (웹 상태 변화 확인)
3. 기사: 저장된 배송 작업 완료 → 로컬 로그 기록
4. 로봇: 공유 통로와 선행 작업 충돌 여부 확인 → 안전한 작업만 배정
5. 물류센터: 입출고 처리 및 물품 위치 스캔
6. 중앙 서버 재시작 → 백업 로그 동기화 → 실물 위치/중복 검증 후 정상 전환

## 5. 검증 계획
| KPI | 정의 | 비교 조건 |
|---|---|---|
| 작업 지속률 | 장애 중 안전하게 완료된 작업 / 장애 기간 처리 대상 | 백업 없음 vs 사전 백업 vs DAOS |
| 전환 지연 | 실제 장애 시각부터 백업 모드 활성화까지 | 동일 장애 주입 |
| 중복 작업률 | 중복 처리된 작업 수 / 전체 처리 작업 수 | 반복 요청/복구 재시도 |
| 위치 불일치 | 복구 후 불일치 물품 수 | 위치 스캔 및 로그 대조 |
| 복구 완료 시간 | 중앙 복귀부터 검증·정상 전환까지 | 같은 작업·장애 규모 |

**주의:** 공개된 실제 기업 사고는 문제 동기이며, 시뮬레이션 수치는 실제 현장 성과로 단정하지 않는다.

## 6. 단계별 개발 이슈
- Phase 1: 저장소 구조, 실행 문서, 데이터 계약, 테스트 환경
- Phase 2: 중앙 서버/백업 엔진, 상태 전환, 작업 로그
- Phase 3: Driver PWA 오프라인 저장/동기화
- Phase 4: Robot 웹 + 의존성 그래프 + 점유권/리스 시뮬레이션
- Phase 5: Factory 웹 + 실물 위치 대조 + 충돌 검증
- Phase 6: 통합 테스트, 실험 데이터, 발표 자료

## 7. 역할 분담 제안
- 담당 A: 공통 엔진/API/데이터베이스
- 담당 B: Driver 앱/오프라인 기능
- 담당 C: Robot 웹/안전한 스케줄링
- 담당 D: Factory 웹/테스트 및 시각화

인원과 역할은 실제 팀 상황에 맞춰 조정한다.

## 8. 추가 팀 제안 — 로봇의 단기 독립 운영과 사후 동기화 (2026-11-07)

### 팀에서 제안한 문제
- VDA/VDMA가 공동 추진한 **VDA 5050 통신 인터페이스**를 활용하는 중앙 관제 시스템(MCS/FMS)과 로봇 사이에 네트워크 장애가 발생할 수 있다.
- 중앙 관제 또는 메인 서버에서 더 이상 새 작업 정보를 받지 못하면 로봇 및 개별 설비의 운영이 중단될 수 있다.
- 통신 복구 후 장애 중 생성된 작업 내역이 중앙 DB에 반영되지 않으면 상태 불일치와 중복 작업 위험이 생긴다.

> 용어 메모: **VDMA는 협회 이름**이며 로봇 통신 표준 이름이 아니다. 통신 형식은 **VDA 5050**이라고 표기한다. 표준 메시지를 사용한다고 해서 통신 장애 중 자율 작업이나 안전성이 자동 보장되지는 않는다.

### 팀이 제안한 동작
1. 정상 운영 중 로봇/장비에 **단시간 작업 수행에 필요한 기존 작업 명령, 경로 정보, 운영 규칙**을 사전 저장한다.
2. 중앙 관제 시스템 및 메인 서버 연결이 끊기면 장애를 감지하고 비상 운영 모드로 전환한다.
3. 로봇이 사전 할당받은 작업 중 **작업 의존성·공유 자원 점유권·현재 안전 상태**가 확인된 것만 독립 실행한다.
4. 장애 중 로봇의 상태 변화, 수행 작업, 이동 결과, 오류 및 이벤트를 로컬 저장소에 기록한다.
5. 연결 복구 시 로컬 작업 이벤트를 중앙 관제로 전달하고, 중앙 DB에 반영하기 전 **고유 이벤트 ID·중복·작업 상태·실제 물품 위치**를 검증한다.
6. 중앙 시스템과 상태가 일치하는 것을 확인한 다음 정상 관제권을 복귀시킨다.

### 안전·구현 경계
- **단기 운영**과 배송기사의 **2~3일 데이터 백업**은 서로 다른 범위다. 로봇 작업 권한과 공유 통로 점유 정보는 수일간 유효하다고 가정하지 않는다.
- 공유 공간 점유 상태를 확인할 수 없거나, 사전 승인된 경로를 벗어나거나, 다른 로봇과 충돌 가능성이 있으면 해당 작업을 보류한다.
- 로봇 자체 통신·센서·안전 기능이 고장 난 경우에는 비상 관제만으로 운행을 계속하도록 하지 않는다.
- 초기 시연은 **가상 로봇과 가상의 관제 메시지**로 검증하고, 실제 VDA 5050 규격 준수 여부는 별도 테스트로 입증한다.

### 시연·평가 항목
- 메인 MCS 연결 종료 → 가상 로봇의 비상 모드 전환
- 서로 독립적인 작업은 이어가고, 공유 통로 충돌 작업은 대기
- 로봇별 이벤트 로그 보존 및 중앙 복구 후 동기화
- 중복 작업 건수 / 안전한 작업 지속률 / 관제권 인계 시간 / 동기화 후 상태 일치율 측정
